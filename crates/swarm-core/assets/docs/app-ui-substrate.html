The App UI Substrate

How an app built on Swarm Core looks. This is the UI part of the architectural substrate: every app draws with the same theme, type, density and chrome, so the swarm's tools look and work alike. The app architecture contract says why a colour is a token and a word is a catalog entry; this page says what they are.

1Principles

  • One home for each value. Colours live in the engine's theme module; metrics, faces and sizes, and icon codepoints each have one module of their own. A call site never writes a colour, a size, a codepoint or a word.
  • The theme is data. The palette sits in the engine, below the toolkit, so the ui.theme command gives every surface (the window, the CLI, MCP, a test) the same tokens and ranges. The UI crate's theme module is the one place a toolkit colour is made.
  • A colour is named for what it means. Drawing code asks for error or selection, never for a hue. An identifier's colour comes from a range, by a fixed hash, so it is the same on every run, surface and machine.
  • Readable by rule, checked by test. Contrast is measured (WCAG 2) in both looks; a value that falls short is either nudged and noted, or kept and recorded with its ratio and the reason.
  • No network. Fonts and the app icon are embedded, so the desktop and browser builds draw the same offline.
  • Words from the catalog. Every word a person reads is an entry in the string catalog. scan holds both rules: ui-colours finds a colour made outside the theme module, ui-strings a string literal outside the catalog.

2Looks, and how the theme is applied In the skeleton

The theme has two looks, dark and light (Look); each token and each range entry has a value in both.

  1. The engine's theme.rs holds the palette as constants: TOKENS and RANGES.
  2. ui.theme returns it as data (ThemeData): each token's name, meaning and #RRGGBB in each look, each range's entries with their text background and border in each look, and the corner radius.
  3. The UI crate's theme::apply(ctx) runs once, when the window starts: it installs the faces, and gives both of egui's appearances their visuals, the text styles and the density (ctx.style_mut_of), so egui chooses between them every frame and following the system's look works live.
  4. Drawing code asks Theme::of(ui.visuals()) while it draws and never caches it: the look can change between frames.

An app may offer people a choice. One of the swarm's tools has Options › Theme: System, Dark (its default) and Light, saved with the UI state.

Corner radius In the skeleton

2 px in both looks, for window_corner_radius, menu_corner_radius and every widget state's corner_radius: windows, menus and controls are near-square. It is the engine theme's CORNER_RADIUS, which ui.theme gives as corner_radius and Theme::visuals sets. The dock (section 10) is square.

5Ranges: colours for identifiers In the skeleton

A range is a set of colours for telling things apart. There are two ways to choose from one:

  • at(n) takes a number in order: entry n % size.
  • pick(id) hashes an identifier with 64-bit FNV-1a over the UTF-8 it displays as, so pick(7) is pick("7"). The hash is fixed and documented, unlike std's DefaultHasher, so an id's colour never changes between Rust releases.

Every entry also has a text background, behind_text: its HSL lightness held at most 0.5 in dark or at least 0.5 in light, then moved further until strong text on it reaches 4.5:1, its hue and saturation kept. It has a border too, darker: each channel × 0.8, rounded down, which outlines a filled bar or mark. ui.theme gives both with each entry, and the skeleton's swatch view draws them. Below, each entry shows its fill in its border, then strong text on its text background, on each look's background.

6Contrast In the skeleton

Measured by WCAG 2 relative luminance, in each look, by the theme's tests.

Text: at least 4.5:1TEXT_CONTRAST, WCAG 2 1.4.3. Every token read as text meets it on what it is drawn on, and strong text on any entry's text background meets it by construction.
Fills and edges: at least 3:1FILL_CONTRAST, WCAG 2 1.4.11: control_border against background and panel, and each range entry against background.
A shortfall is nudged or recorded, never silentrange16 and range32 are nudged: an entry under 3:1 moves lighter in dark (darker in light) in CIELAB lightness, keeping its hue, and its comment gives the original and its ratio. 9Icons In the skeleton

In crates/ui/src/icons.rs.

  • Glyphs: Font Awesome Free 6.7.2 Solid (the font SIL OFL 1.1, the icons CC BY 4.0, whose attribution the embedded font's own metadata carries; an app with an About credits it there too), at the body size. Codepoints are named constants in icons, each the icon's Font Awesome name, never literals; a test checks each is in the embedded font.
  • Which icon goes where is data: a table (BY_COMMAND) maps a command id to its icon, so a new command gets its menu icon with no menu code, and one function (for_pane) maps each dock pane to its icon, for its tab (section 10). An app with nested menus maps them the same way.
  • Alignment: menu icons sit in a fixed 16 pt column (Font Awesome's widest glyphs are 1.25 em); a command with no icon keeps the empty column, so labels line up.
  • Colour: an icon takes its widget's text colour, so a disabled item's icon dims with it; a decorative icon takes a token.
  • Accessibility: an icon is an atom egui leaves out of a widget's accessible name, so a widget is named by its text; an icon-only button gets a name and a tooltip of its own; a dock tab's title is text with the icon in it.

10The dock In the skeleton

The window under the menu bar is a dock (crates/ui/src/dock.rs): its panes as egui_tiles tiles (rerun-io, MIT OR Apache-2.0, made for egui 0.37), tabs and splits a person drags and resizes. The skeleton's panes are the command list (commands) and the open command's view (view); the default layout puts the list on the left, 300 per mille of the width, and the view beside it.

The UI state is the layout's source of truthThe layout is the UI state's dock, a small typed tree (DockNode: tabs of panes by id with the one shown, or a split across or down into parts, each with its share per mille) that ui.set sets and ui.inspect reads. Each frame the dock is built from it when it changed (an agent's ui.set, a restored launch), drawn, and read back: what a person dragged or resized goes to the state through ui.set. egui_tiles' own saved state is never loaded.
A hostile layout can't break itui.set refuses a layout deeper than 6 or holding more than 32 items, a split with no parts or a share out of 1–1000, empty tabs, or a pane the dock doesn't have; a saved file with such a layout is refused as malformed. Whatever layout it is given, the dock shows each pane once: one left out is added, one named twice is shown once. Hiding the command list (show_list) hides its tile.

11The window and the app icon In the skeleton

In apps/<app>/src/window.rs and place.rs, and crates/ui/src/icon.rs.

  • Frame: the system's own title bar and frame: no custom decorations, no transparent window.
  • Title: the product name.
  • Size and place: the app keeps them itself, not eframe (persist_window: false), in a file beside the UI state's (--ui-state <file>; the window's is <file> with .window.json). It saves only a normal window's rectangle, and maximized on its own: one closed minimized, maximized or full screen keeps the last normal one. At launch it reads the monitors before the window opens (the app runs eframe on its own event loop, place::Launch) and restores the rectangle only when at least half of it is on a connected monitor and it is over the minimum (640 × 400); otherwise the window opens at its default size (1280 × 800, no more than nine tenths of the monitor), centred on the primary monitor. The file is read through the backends' capped read and written through their atomic writer, as hostile input.
  • Renderer: glow (OpenGL), the skeleton's default: small, and enough for its window. An app that needs more switches to wgpu in its window's eframe features; one of the swarm's tools does, asking the GPU for its own largest texture side so a window across monitors fits, with vsync on and an environment variable to turn it off when measuring frame times.
  • App icon: a generic one drawn in code from the theme's palette, with no third-party artwork: a dark tile (header to base) holding a list of three commands, each a text bullet and a bar in the series' first colours. The window uses it at 256 px. An app replaces it with its own, drawn the same way. A browser favicon or a Windows .ico (embedded in the exe with its version info by a build.rs) is the app's to add: generated from the drawing code and checked in, with a test that fails when they drift from it.

12Menus In the skeleton

The menus are the commands' menu paths and shortcuts (app-architecture.md › The minimum interfaces): the UI maps the same data to wherever the platform puts menus, and no command changes for it.

  • Windows and Linux: the window's own bar. egui's menu bar across the top of the window, a menu per first part of the paths, each item with its icon, its shortcut and, when it can't run now, greyed out with why.
  • macOS: the system menu bar. The menus are at the top of the screen and the window draws none: the dock fills it under the title bar. crates/ui/src/native_menu.rs makes the bar as plain data from Shell::menus() (tested on every platform), and apps/<app>/src/macos_menu.rs hands it to AppKit with muda (tauri-apps, MIT OR Apache-2.0) on the window's own event loop. Automatic window tabbing is off, so AppKit adds no tab items. If muda can't make the bar, the window draws its own and says so on stderr.

  • Where an app's own items go. A command whose menu path starts with App (App/Settings…, with Mod+Comma: preferences) is in the application menu after About on macOS, and in a menu named App elsewhere. The app's own info (Help/App info, the skeleton's app.info) stays in Help on every platform: About is the system's panel, not a command.
  • Quit closes the window as its close button does, so the UI state and the window's place are saved; the system's other items are the system's to run.
  • A click is a click. A native item activates its command's row as a click in the window's bar does (Shell::activate), through the one dispatch, so consent and unavailable behave the same. Each item is greyed out while its command can't run now, set again each frame from the rows.
  • A shortcut fires once. On macOS it is the item's key equivalent alone: AppKit takes it before the window sees the key, so egui never gets it too. A command's shortcut that a system item takes (⌘Q, ⌘H, ⌥⌘H, ⌘M) keeps its item without the key. Mod is Command; Plus is the = key.
  • Layers. muda is a toolkit to layers: the UI layer and the apps built on it may link it, nothing below. The skeleton links it in the windowed app, for macOS only (no GTK elsewhere).

13Changing the UI substrate

  1. A colour is a token in the engine's theme.rs, named for what it means, with a value in each look, in TOKENS. Its contrast is measured where it is read: a shortfall is nudged and noted, or kept in KEPT_SHORT with its ratio and why. Change this page and app-ui-substrate.md with it: their test fails on a colour that differs.
  2. An identifier's colour comes from a range, by pick or at, never a colour of its own.
  3. A metric goes in density, a text size in fonts, an icon in icons, each with a doc comment saying where its value comes from.
  4. A new command gets its icon in the command table, and a new pane its icon in the pane mapping.
  5. Every word a person reads is in the string catalog.
  6. Check a UI change by eye: render it offscreen and put the picture on the merge request.
