Every action is a command. Every surface is an adapter.

An app built by a swarm on Swarm Core is headless first. Each thing it can do is one typed command in one registry. The CLI, JSON lines on stdio, the loopback socket, MCP and the window all call the same dispatch, so a person or an agent can run the whole app without a window.

This is the architectural substrate: the shape Swarm Core gives every app before the swarm writes its first feature.

The swarm starts from a skeleton that already has this shape (swarm-core init --app) and is held to it by checks that run in every gate. Select a layer to see what lives there.

Outside the stack

One command, four surfaces

Adding a command adds it everywhere. No transport is edited, and none names a command.

A command is a Rust type. Registering it is the only way a command spec gets built, so none exists without schemas or declared effects. Every surface derives its own name from the id by one function.

  • id area.name, lower case, 64 characters at most, never renamed once released
  • params, result Rust types; their JSON Schemas are generated, never hand-written
  • effects what it can change outside memory: writes files, runs code, network, device
  • requires shared conditions, such as an open project
  • enabled whether it can run now, and why not; cheap, reads memory only
  • menu, shortcut plain text (File/Open recent, Mod+O), so no lower layer links a toolkit

CLI

app run project.open_recent

JSON lines and the socket

{"id": 1, "method": "project.open_recent", "params": {}}

MCP

tools/call  project-open_recent

Tools are generated from the registry. The input schema is the command's params schema.

One dispatch

What happens to a call, in order, and the stable error code each step can answer with.

  1. Look the command up by idunknown_command
  2. Check the params against the command's type; the error names the wrong keybad_params
  3. Check it is enabled: its requirements, then its own check. The menu's greyed state comes from this same functionunavailable
  4. Refuse an effect the caller hasn't consented toconsent_required
  5. Run it. A slow run polls the cancel token that a dropped connection, a deadline or the UI setscancelled, not_found, too_large
  6. Catch a panic, so a bug never takes the surface downinternal

Every failure is one type on every surface: a code, a message, and a remediation that is never empty. A consumer classifies a failure by its code, never by its message.

The window is a client

Nothing the UI does is untestable without a window.

The UI draws memory and calls commands on workers. It never writes a file, starts a program, or blocks its own thread on a call. It asks; it doesn't compute.

Its state is data

Open views, selection, scroll and layout are plain versioned data. ui.inspect reads it and ui.set changes it, so an agent drives the window the way a click does.

It draws what a command returned

No totals, filters or derived state in a view. A test draws a frame headlessly and compares its text with the command's typed result.

Colours from the theme, words from the catalog

Drawing code makes no colour and writes no string. Text tokens are measured at 4.5:1 contrast, range colours at 3:1. An identifier's colour is a fixed hash of its id, the same on every machine.

Changes ship with pictures

A UI change carries before and after screenshots, rendered by a script of commands so the picture is the same each time.

Built not to crash or hang

A hostile file or a malformed frame is the normal case, not the rare one.

Never crash

  • No unwrap, expect or panic! in production code, and no indexing on input
  • Arithmetic on input is checked; recursion and allocation are bounded
  • A crash fix ships the input that crashed as a test

Never hang on another program

  • One process module starts every child
  • A wall-clock deadline and an idle deadline
  • Output is capped and drained on its own threads
  • The child's whole process group is killed on timeout, cancel and drop

Never hang on a lock

  • The app's own lock times out with an error that names it
  • std::sync::Mutex is refused by the linter
  • One lock read per statement

State on disk

  • Versioned, with a migration from every earlier version
  • A file from a newer version is refused, never overwritten
  • One atomic writer: a temporary file, flushed, then renamed
  • Saved before memory changes

No secrets out

A result, a log line or an error never carries a token, key or password. Secret settings are stored and shown redacted.

Tests touch nothing real

Temporary directories for config and state, no network, no tool the machine may lack.

What holds each rule

Every rule names its check. Five run in cargo xtask ci; review covers what no tool can.

Rulelayersscanclippyconformanceown testsreview
checked by a tool in the gate checked by a reviewer

layers reads each crate's declared layer. scan finds forbidden constructs outside their one home, such as a process start or a file write. conformance runs every command through every surface with hostile and valid params and holds the answers to agree.

One gap a tool doesn't cover yet

Only backends touches the outside. layers stops a model or domain crate depending on a backends crate, and scan finds a process start or a file write in any other crate. A direct file read or network call in those layers is not scanned for yet. That is the reviewer's dot in the Layers row.

The swarm's commands

Each runs as cargo xtask <name> in the app's repo. Swarm Core serves all but the last two.

A worker's

claim
Take an issue: label it, branch from main and open a draft PR.
ready
Run ci --changed on your branch, then mark the PR ready for the coordinator.
prwatch
Watch your PRs: merge state, comments, and what each needs from you next.
finish
End a session: check nothing is owed, remove clean worktrees and merged branches.

The coordinator's

stack
Rebase the ready PRs into one stack, in dependency order.
gate
Run the gate on that stack. gate --daemon runs stack, gate and land unattended.
land
Merge the gated stack, and only what was gated.
tidy
Clear a merged issue's claim label and leftovers.
fullgate
Run the whole ci on main when it has gone unverified too long.

Who depends on whom, and who talks to whom

Grey arrows are compile-time dependencies and always point down. Blue arrows are what moves at runtime, in the direction it moves.

  • A crate may depend on any layer below it; only the main paths are drawn. Nothing ever depends upward, so the engine never calls the UI or a transport: replies travel back as return values and messages.
  • The UI and the transports never talk to each other. Both reach the app only through the engine's dispatch.
  • With mcp --attach, the CLI's MCP server sends its calls to a running app's socket instead of its own engine.
  • Only backends reaches outside the app. The engine decides what is stored and when, and hands backends the bytes.
  • The domain and the model talk to nothing. The engine hands them data and takes their answers.
